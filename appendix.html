נספח — נושאים מתקדמים

המדריך הראשי מכסה את הנושאים שנבדקו בשאלות התרגול. הנספח הזה משלים אותו: הוא מכסה את כל שאר החומר שמופיע במצגות הקורס אך לא במדריך הראשי — לכיסוי מלא של הסילבוס.

איך להשתמש אם כבר סיימת את המדריך הראשי ואת מרגישה בטוחה בשאלות התרגול — עברי לכאן להעמקה. כל מודול בנוי כמו במדריך הראשי: הסבר → דוגמה → מלכודות. בסוף יש בוחן מתקדם עם 15 שאלות חדשות בסגנון אמריקאי.

מה מכוסה כאן ולמה זה חשוב הנושאים כאן (במיוחד operator=, מחלקות תבנית, חריגים לעומק ו-vtable) הם חומר קלאסי למבחני OOP. גם אם לא הופיעו בשאלות התרגול, כדאי להכיר אותם.

A1 · אופרטור השמה וכלל השלושה המלא

מה קורה כשכותבים a = b על אובייקטים, ולמה זה אחד הנושאים החשובים ביותר.

ההבדל בין העתקה להשמה

בנאי העתקהאופרטור השמה operator=
מתייצירת אובייקט חדש: B b = a;אובייקט קיים: b = a;
מצב היעדריק (עוד לא אותחל)כבר מחזיק נתונים (אולי משאב דינמי)

מימוש נכון של operator= (עם משאב דינמי)

שלושה דברים חובה: (1) בדיקת השמה-עצמית, (2) שחרור המשאב הישן, (3) העתקה עמוקה, ולבסוף החזרת *this.

FVector& operator=(const FVector& other) {
    if (this != &other) {      // 1. הגנה מפני a = a
        delete[] items;         // 2. שחרור המשאב הישן
        size = other.size;
        items = new float[size]; // 3. הקצאה חדשה + העתקה עמוקה
        for (int i=0; i<size; i++) items[i]=other.items[i];
    }
    return *this;         // מאפשר שרשור: a = b = c
}
מלכודת: בלי בדיקת השמה-עצמית אם משמיטים את if(this != &other), אז a = a יבצע קודם delete[] items — ובכך ימחק את הנתונים שמהם אנחנו מנסים להעתיק. התוצאה: זבל / קריסה.

כלל השלושה (Rule of Three) — הניסוח המלא אם מחלקה צריכה אחד מהשלושה, כמעט תמיד היא צריכה את כולם: הרסן, בנאי העתקה, operator=. הסיבה: ברירת המחדל של הקומפיילר מבצעת העתקה שטחית (מעתיקה מצביע, לא את מה שהוא מצביע עליו).

מלכודת בירושה: operator= ברירת המחדל = shallow copy גם אם מחלקת הבסיס מימשה operator= נכון, ליורשת שמוסיפה משאב דינמי משלה יש operator= אוטומטי שמבצע העתקה שטחית של המשאב החדש. הפתרון: לממש operator= ליורשת, שקורא קודם ל-Base::operator=(other) ואז מעתיק עמוק את השדות שלה.

A2 · העמסת אופרטורים מתקדמת

מעבר ל-[], << ו-++ שכבר ראית — כאן: +, member מול global, אופרטור המרה, ו-operator().

member מול global (friend) — ולמה זה משנה

כשמעמיסים אופרטור בינארי כמתודה, האופרנד השמאלי חייב להיות האובייקט שלנו. לכן a + 5 עובד (a הוא האובייקט), אבל 5 + a לא — כי האופרנד השמאלי הוא int.

הכלל אם האופרנד השמאלי אינו מהמחלקה שלך (למשל 5 - a, cout << a), האופרטור חייב להיות פונקציה גלובלית (לרוב friend), לא מתודה. לסימטריה מלאה מגדירים לרוב את שתי הגרסאות.

// גלובלי — מאפשר גם 5 - a וגם a - 5
friend Money operator-(const Money& a, const Money& b);

אופרטור המרה (conversion operator)

מאפשר לאובייקט "להתחפש" לטיפוס אחר אוטומטית. שימי לב: אין טיפוס החזרה כתוב — הוא נקבע מהשם.

class Money {
    int agorot;
public:
    operator int() const { return agorot; }  // המרה ל-int
};
Money m;
int x = m;   // מפעיל את אופרטור ההמרה אוטומטית

operator() — אופרטור הקריאה לפונקציה

מעמיסים את הסוגריים כדי "לקרוא" לאובייקט כאילו הוא פונקציה. זה הבסיס ל-functors (מודול A11).

struct Adder {
    int operator()(int a, int b) const { return a+b; }
};
Adder add;
cout << add(2, 3);   // 5 — נראה כמו פונקציה, זה אובייקט
operator+ מחזיר by value a + b יוצר אובייקט חדש (הסכום), ולכן מחזירים by value (עותק). לעומת זאת operator+= משנה את האובייקט הקיים ומחזיר *this ב-reference.

A3 · טיפול בשגיאות — חריגים לעומק

מעבר ל-throw בסיסי: מחלקות חריג משלך, catch מרובה, catch-all, וניקוי לפני זריקה.

למה לא קודי שגיאה?

החזרת קוד שגיאה (למשל -1) בעייתית: אפשר להתעלם ממנו, צריך if אחרי כל קריאה, והוא לא נושא מידע. וחשוב: לבנאים ולהרסנים אין ערך החזרה — אז אין להם דרך לדווח על שגיאה חוץ מחריג.

מחלקת חריג משלך

אפשר לזרוק כל דבר — מספר, מחרוזת, או אובייקט. אובייקט עדיף כי הוא נושא מידע.

class DivByZero {
    string msg;
public:
    DivByZero(string m) : msg(m) {}
    string what() const { return msg; }
};
if (b == 0) throw DivByZero("חלוקה באפס");

catch מרובה ו-catch-all

כללים חשובים תופסים אובייקט חריג by reference (catch(DivByZero& e)) כדי למנוע slicing. אפשר כמה בלוקי catch לפי טיפוס. catch(...) תופס הכל — וחייב להיות אחרון, אחרת הוא "יבלע" את כל השאר.

try { risky(); }
catch(DivByZero& e) { cout << e.what(); }
catch(int code)       { cout << code; }
catch(...)             { cout << "שגיאה לא ידועה"; }  // חייב אחרון
מלכודת: דליפת זיכרון בזריקה אם הקצית זיכרון (new) ואז זרקת חריג לפני ששחררת אותו — הזיכרון דולף (ה-stack unwinding לא מריץ delete על מצביעים גולמיים). לכן משחררים לפני ה-throw, או משתמשים ב-RAII.

חריג בבנאי (תזכורת מהמדריך הראשי) אם נזרק חריג בבנאי, האובייקט לא נבנה במלואו ← ההרסן שלו לא ירוץ. משאבים שכבר הוקצו בבנאי צריכים שחרור ידני לפני ה-throw.

A4 · const מתקדם ו-mutable

איפה בדיוק שמים const, ומה עושים כשרוצים לשנות שדה גם על אובייקט const.

ארבעה מקומות ל-const

מיקוםמשמעות
const int xהמשתנה עצמו לא ניתן לשינוי
const int& get()הערך המוחזר לא ניתן לשינוי דרך ה-reference
void f(const T& p)הפרמטר לא ישונה בפונקציה (מעביר בלי להעתיק)
int get() constהמתודה לא משנה את האובייקט → מותר לקרוא לה על אובייקט const
הכלל הגדול של const-correctness על אובייקט const מותר לקרוא רק למתודות שמסומנות const. אם מתודה לא מסומנת const — קריאה אליה מאובייקט const היא שגיאת קומפילציה.

const Name gabi("Gabi");
gabi.getName();   // OK אם getName() const
gabi.setName(...);  // שגיאה! setName משנה את האובייקט

mutable — החריג לכלל

שדה שמסומן mutable מותר לשינוי גם בתוך מתודת const וגם על אובייקט const. השימוש הקלאסי: caching — לשמור תוצאה מחושבת בלי "לשבור" את ההבטחה של const.

class Circle {
    double r;
    mutable double cachedArea;   // ניתן לשינוי גם ב-const
    mutable bool valid = false;
public:
    double area() const {      // const — אבל מעדכן cache
        if (!valid) { cachedArea = 3.14*r*r; valid = true; }
        return cachedArea;
    }
};

A5 · static לעומק

שדה משותף לכל המחלקה, אתחולו מחוץ למחלקה, ומתודות static.

שדה static — עותק אחד לכל המחלקה

שדה רגיל קיים בכל אובייקט בנפרד. שדה static קיים פעם אחת ומשותף לכל האובייקטים. שימוש קלאסי: לספור כמה אובייקטים נוצרו.

מלכודת: חובה לאתחל מחוץ למחלקה הכרזה על שדה static בתוך המחלקה לא מקצה לו זיכרון. חייבים שורת הגדרה אחת מחוץ למחלקה, אחרת מקבלים שגיאת קישור (linker error).

class Player {
    static int count;      // הכרזה בלבד
public:
    Player()  { count++; }
    ~Player() { count--; }
    static int getCount() { return count; }  // מתודה static
};
int Player::count = 0;    // ← הגדרה + אתחול, מחוץ למחלקה. חובה!

cout << Player::getCount();  // קוראים דרך שם המחלקה, בלי אובייקט
מתודה static אין לה this (היא לא שייכת לאובייקט מסוים), ולכן היא יכולה לגשת רק לשדות ומתודות static. קוראים לה דרך Class::method().

מכסה: מצגת 3.4

A6 · ירושה — דריסה, הסתרת שם וקריאה לבסיס

מה קורה כשליורשת ולבסיס יש מתודה או שדה באותו שם.

דריסה (overriding) וקריאה מפורשת לבסיס

יורשת יכולה להגדיר מחדש מתודה של הבסיס. עדיין אפשר לקרוא לגרסת הבסיס במפורש עם Base::method().

class Stack { public: void Push(int x){} };
class SumStack : public Stack {
public:
    void Push(int x) {
        Stack::Push(x);   // קריאה מפורשת לגרסת הבסיס
        // ... לוגיקה נוספת (עדכון סכום)
    }
};

⭐ הסתרת שם (Name Hiding)

מלכודת חשובה אם היורשת מגדירה מתודה בשם מסוים, היא מסתירה את כל העומסים (overloads) של אותו שם בבסיס — גם בעלי חתימה שונה. לכן אם הבסיס מגדיר f() והיורשת מגדירה f(int), אז d.f() (בלי פרמטר) לא יתקמפל — למרות ש-f() קיים בבסיס.

class A { public: void f() {} };
class B : public A { public: void f(int x) {} };
B b;
b.f(5);   // OK
b.f();    // שגיאה! A::f() הוסתר. פתרון: b.A::f() או using A::f;

הסתרת שדות

אותו רעיון לשדות: אם ליורשת שדה y ולבסיס גם y, הגישה הרגילה מגיעה לשדה של היורשת. לשדה הבסיס: A::y.

מכסה: מצגת 5

A7 · הרשאות ירושה — private / protected

איך סוג הירושה משנה את הנגישות, ואיך "לחשוף מחדש" חבר בודד.

תזכורת: השפעת סוג הירושה

חבר בבסיסpublic inheritanceprotected inheritanceprivate inheritance
publicpublicprotectedprivate
protectedprotectedprotectedprivate
privateלעולם לא נגיש ליורשת
מה זה אומר בפועל ירושת private אומרת "יש-לי" יותר מ"אני-סוג-של". כל החברים הציבוריים של הבסיס הופכים לפרטיים ← לא נגישים דרך אובייקט של היורשת, ולא עוברים הלאה ליורשות של היורשת.

חשיפה מחדש (re-exposing) של חבר בודד

אחרי ירושת private/protected, אפשר "להחזיר" חבר יחיד לרמת public בעזרת הצהרת using (או שם מלא) באזור ה-public של היורשת.

class A { public: int x; void g(){} };
class B : private A {   // הכל הופך private
public:
    using A::g;          // חושף מחדש רק את g כ-public
};
B b;
b.g();   // OK — נחשף מחדש
b.x;     // שגיאה — x נשאר private

A8 · איך פולימורפיזם עובד באמת (vtable)

המנגנון מאחורי virtual — נושא שאוהבים לשאול עליו "how it works".

קישור סטטי מול דינמי

שני סוגי קישור קישור סטטי (בזמן קומפילציה): הקומפיילר מחליט איזו פונקציה לקרוא לפי הטיפוס המוצהר. זו ברירת המחדל ב-C++.
קישור דינמי (בזמן ריצה): ההחלטה נדחית לזמן הריצה לפי הטיפוס האמיתי. מופעל רק כשהמתודה virtual.

שימי לב: זה שונה מ-Java, שבה כל המתודות דינמיות כברירת מחדל. ב-C++ צריך לכתוב virtual במפורש.

vtable ו-vfptr

ברגע שלמחלקה יש מתודה virtual אחת, הקומפיילר יוצר עבורה טבלת פונקציות וירטואליות (vtable) — מערך של כתובות של המתודות הווירטואליות. כל אובייקט מקבל מצביע נסתר (vfptr) לטבלה של המחלקה האמיתית שלו.

// כשכותבים:
p->g();
// הקומפיילר מתרגם בערך ל:
(*(p->vfptr)[indexOf_g])(p);   // חיפוש הכתובת בטבלה בזמן ריצה

לכן קריאה וירטואלית "יודעת" להגיע לגרסה הנכונה: היא לא מקודדת מראש, אלא נשלפת מהטבלה של האובייקט האמיתי.

מסקנות מעשיות לכן פולימורפיזם עובד רק דרך מצביע/reference (לאובייקט יש vfptr אמיתי), ולא ב-slicing. ולכן חשוב הרסן virtual — כדי שגם ההרסן ייבחר מהטבלה הנכונה.

מכסה: מצגת 6

A9 · מחלקות תבנית (Template Classes)

לא רק פונקציות תבנית — מחלקה שלמה שעובדת על כל טיפוס.

הגדרת מחלקת תבנית

template <class T>
class Vector {
    T* items;
    int size;
public:
    T& operator[](int i);
    void print() const;
};

Vector<int> vi;        // גרסה ל-int
Vector<Student> vs;    // גרסה ל-Student
מלכודת: הגדרת מתודה מחוץ למחלקה כשמגדירים מתודה של מחלקת תבנית מחוץ למחלקה, חייבים לחזור על שורת ה-template ולכתוב את שם המחלקה עם <T>:

template <class T>
void Vector<T>::print() const { /* ... */ }

התמחות (specialization)

לפעמים טיפוס מסוים דורש מימוש שונה. אפשר לספק גרסה ייעודית. דוגמה קלאסית: max על מחרוזות דורש strcmp, לא <.

template <>               // התמחות מלאה
const char* maxT(const char* a, const char* b) {
    return (strcmp(a,b) < 0) ? b : a;
}

שילובים

עם פולימורפיזם: Vector<Employee*> — וקטור של מצביעים שמאפשר קריאות וירטואליות.
ירושה ממחלקת תבנית: אפשר לקבע טיפוס (class B : public A<int>) או להישאר כללי (template<class T> class B : public A<T>).

תבניות מול פולימורפיזם שתיהן מאפשרות קוד כללי. תבניות = "כל טיפוס", נפתרות בזמן קומפילציה (מהיר, אבל מנפח את הקוד — גרסה לכל טיפוס). פולימורפיזם = "משפחת טיפוסים עם אב משותף", נפתר בזמן ריצה.

מכסה: מצגת 9

A10 · קבצים לעומק

מעבר לכתיבה/קריאה בסיסית: היררכיית הזרמים, מיקום בקובץ, מצבי פתיחה, וקבצים בינאריים.

היררכיית הזרמים

קבצים בינאריים וסריאליזציה

כתיבה בינארית קומפקטית ומהירה: כותבים את הבייטים הגולמיים.

int x = 42;
f.write((char*)&x, sizeof(x));   // כתיבה בינארית
f.read((char*)&x, sizeof(x));    // קריאה בינארית
מלכודת: איך יודעים מה קראנו? כשטוענים אובייקטים פולימורפיים מקובץ, צריך לדעת איזה סוג לבנות. הפתרון: לשמור בקובץ גם קוד-טיפוס (למשל שני תווים מ-typeid) לפני כל רשומה, ולפיו להחליט איזה אובייקט ליצור בטעינה.

A11 · STL לעומק

מכולות, אלגוריתמים, איטרטורים מבפנים, ו-functors שמוזרקים לאלגוריתמים.

שלושת חלקי ה-STL

מכולות (containers), אלגוריתמים גנריים, ואובייקטי פונקציה (functors) שמחברים ביניהם.

אלגוריתמים נפוצים (<algorithm>)

אלגוריתםמה עושה
for_eachמפעיל פעולה על כל איבר
count_ifסופר איברים שמקיימים תנאי (predicate)
find_ifמוצא את הראשון שמקיים תנאי
sortממיין (אפשר לפי comparator מותאם)
remove_ifמזיז איברים... (ראי מלכודת)
מלכודת קלאסית: remove_if לא מוחק! remove_if לא באמת מוחק איברים מהמכולה (הוא לא יכול — אין לו גישה אליה). הוא מזיז את האיברים שנשארים לתחילת המכולה ומחזיר איטרטור ל"סוף החדש". כדי למחוק באמת חייבים לקרוא אחריו ל-erase. זה נקרא erase-remove idiom:

v.erase( remove_if(v.begin(), v.end(), IsEven()), v.end() );

Functors מוזרקים לאלגוריתמים

functor = struct עם operator(). מעבירים אותו לאלגוריתם כדי לקבוע את הלוגיקה בלי לשנות את המכולה.

struct OlderThan {
    int age;
    OlderThan(int a):age(a){}
    bool operator()(const Student& s) const { return s.age > age; }
};
int n = count_if(v.begin(), v.end(), OlderThan(18));

איטרטורים — הרעיון מבפנים

מצביע גולמי הוא איטרטור מושלם למערך (יש לו ++, *, ==). אבל על רשימה מקושרת מצביע נכשל, כי הזיכרון לא רציף. לכן כל מבנה נתונים מספק איטרטור משלו שמעמיס את אותם אופרטורים — וכך אלגוריתם גנרי אחד (כמו find) עובד על כולם בלי לדעת מה המבנה הפנימי.

מודל האיטרטור begin() = האיבר הראשון, end() = "אחרי האחרון". לולאה טיפוסית: for(it=c.begin(); it!=c.end(); ++it) use(*it);

A12 · Reference Counting ו-Copy-on-Write

הפרויקט המסכם של הקורס: איך לחלוק נתונים בין אובייקטים בבטחה ובלי בזבוז זיכרון.

הבעיה

העתקה עמוקה (deep copy) בטוחה אבל מבזבזת: אם חמש מחרוזות מכילות אותו טקסט, יש חמישה עותקים. העתקה שטחית חוסכת זיכרון אבל מסוכנת: מי משחרר את הנתון המשותף? מי שישחרר ראשון ישאיר לאחרים מצביע תלוי.

הפתרון: ספירת התייחסויות (Reference Counting)

כל האובייקטים חולקים את אותו נתון + מונה משותף שסופר כמה מצביעים אליו. יוצרים עותק ⟵ המונה עולה. אובייקט נהרס ⟵ המונה יורד. כשהמונה מגיע ל-0 ⟵ משחררים באמת.

class RCString {
    char* str;
    int* refCount;   // מונה משותף — לכן מצביע
    void detach() {     // בהרסן / לפני השמה חדשה
        if (--(*refCount) == 0) { delete[] str; delete refCount; }
    }
public:
    RCString(const RCString& o)      // העתקה = חלוקה + הגדלת מונה
      : str(o.str), refCount(o.refCount) { (*refCount)++; }
    ~RCString() { detach(); }
};

Copy-on-Write (COW) — העתקה בכתיבה

הרעיון כל עוד רק קוראים — חולקים את אותו נתון (חסכוני). ברגע שמישהו רוצה לשנות והנתון משותף (refCount > 1) — יוצרים לו עותק פרטי לפני השינוי, כדי לא לפגוע באחרים.

// operator[] לא-const → כתיבה אפשרית → חייב לשכפל אם משותף
char& operator[](int i) {
    if (*refCount > 1) {        // הנתון משותף → משכפלים
        (*refCount)--;
        str = cloneBuffer(str);   // עותק פרטי
        refCount = new int(1);
    }
    return str[i];             // עכשיו בטוח לשנות
}
// גרסת ה-const מחזירה עותק לקריאה בלבד ולא משכפלת
קשר לעולם האמיתי זה בדיוק העיקרון שמאחורי shared_ptr ומאחורי מימושים ישנים של std::string. הבנת המנגנון הזה מראה שליטה אמיתית ב-Rule of Three ובניהול משאבים.
