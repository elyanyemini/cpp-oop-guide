ברוכה הבאה — נתחיל מאפס

המדריך הזה מלמד את כל החומר של הקורס "השלמות תכנות מונחה עצמים ב-C++", מסודר בדיוק לפי מה שנבחן. אין צורך בידע מוקדם בשפה — כל מושג מוסבר בשפה פשוטה, עם דוגמה קטנה, ועם "מלכודות מבחן".

מה חשוב לדעת על המבחן המבחן אמריקאי: 10 שאלות, לכל שאלה 4 תשובות ורק אחת נכונה. משך: שעה ועשרים. חומר סגור. הרבה שאלות נותנות לך קטע קוד ושואלות "מה יודפס?" או "מה תהיה השגיאה?". לכן העיקר הוא לדעת לקרוא קוד ולעקוב אחריו בראש, לא לשנן הגדרות.

איך להשתמש במדריך

עברי על המודולים לפי הסדר, החל ממודול 0. מודול 0 מלמד את כל אוצר המילים של השפה (מצביע, reference, const, this, מתודה מול פונקציה חופשית ועוד) — כל המושגים שהמודולים הבאים משתמשים בהם. אם משהו בהמשך לא ברור, כמעט תמיד התשובה נמצאת שם. כל מודול בנוי אותו דבר: הסבר מאפס, דוגמה קטנה, ומלכודות מבחן. בסוף כל מודול מצוינות שאלות מהבוחן שהוא מכסה. אחרי שסיימת את כל המודולים — גשי לבוחן האינטראקטיבי ופתרי את כל 20 השאלות. לכל תשובה יש הסבר מלא: למה היא נכונה, ולמה כל מסיח שגוי.

טיפ ללימוד למבחן אמריקאי כשמופיע קוד "מה יודפס", עברי שורה-שורה עם עיפרון דמיוני. שימי לב במיוחד ל: סדר בנאים/הרסנים, האם מתודה היא virtual, והאם אובייקט מועבר by value (העתקה) או by reference. שם מסתתרות רוב המלכודות.

מודול 0 · יסודות השפה

אוצר המילים של C++ — כל מושג שנשתמש בו בהמשך, מוסבר כאן מאפס. אם תרגישי אבודה במודול כלשהו, סביר שהמושג החסר מוגדר כאן. אפשר לחזור לכאן בכל רגע.

למה המודול הזה קיים שאר המדריך מדבר על "מצביע", "reference", "this", "const", "פונקציה חופשית" ו"friend" — ומניח שאת יודעת מה הם. כאן לומדים את כולם, אחד-אחד, בלי להניח כלום.

1. זיכרון ומשתנים

תחשבי על זיכרון המחשב כשורה ארוכה מאוד של תאים ממוספרים. המספר של כל תא נקרא כתובת (address). כשמצהירים משתנה, המחשב שומר לו תא (או כמה) ומכניס לתוכו ערך.

int x = 5;   // המחשב שומר תא, ובתוכו הערך 5. שם התא: x

משתנה רגיל כזה משוחרר אוטומטית כשהפונקציה שבה הוא הוגדר מסתיימת. לא צריך לנקות אותו ידנית.

2. מצביע (pointer)

מצביע הוא משתנה שמחזיק כתובת של תא אחר — במקום ערך רגיל, הוא מחזיק "היכן נמצא" ערך. מסמנים טיפוס-מצביע עם כוכבית: int* = "מצביע ל-int".

int x = 5;
int* p = &x;   // & = "הכתובת של". עכשיו p מחזיק את הכתובת של x
cout << *p;    // * = "לך לכתובת וקח את הערך שם" → מדפיס 5
*p = 9;         // כותב 9 לתא של x. עכשיו x שווה 9!
שני סימנים, אל תתבלבלי &x = "הכתובת של x" (משיגים מצביע). *p = "הערך שבכתובת ש-p מצביע אליה" (הולכים דרך המצביע). זה שני כיוונים הפוכים.

3. הקצאה דינמית — new ו-delete

לפעמים לא יודעים מראש כמה זיכרון צריך — למשל מערך שגודלו נקבע רק כשהתוכנית רצה (המשתמש בוחר). הפעולה new מבקשת מהמערכת בלוק זיכרון בזמן ריצה ומחזירה את הכתובת שלו, ששומרים במצביע.

int size = 3;
float* arr = new float[size];  // "תני לי מקום ל-3 floats". arr מצביע לבלוק
arr[0] = 1.5;
delete[] arr;                     // מחזיר את הזיכרון למערכת
קריטי — זיכרון דינמי לא משוחרר לבד זיכרון שהקצית עם new לא משתחרר אוטומטית. חייבים delete (או delete[] למערך). אם שוכחים — הזיכרון נשאר תפוס לנצח: זה נקרא דליפת זיכרון (memory leak). כלל: כל new חייב delete תואם. זה הלב של הרסנים (מודול 2) ו-Rule of Three (מודול 9).

4. Reference — "כינוי" למשתנה

Reference (מסומן גם ב-&, אבל בהקשר אחר) הוא שם נוסף לאותו משתנה — לא עותק, אלא כינוי. כל שינוי דרך ה-reference משנה את המקור.

int x = 5;
int& r = x;   // r הוא שם נוסף ל-x עצמו (לא עותק)
r = 9;         // שיניתי את x! עכשיו x == 9

ההבדל ממצביע: מצביע הוא משתנה נפרד שמחזיק כתובת (וצריך * כדי להגיע לערך); reference הוא פשוט שם חלופי, ומשתמשים בו כמו במשתנה רגיל. שני המושגים חשובים כי הרבה אופרטורים מחזירים reference — נראה למה במודול 3.

5. const — "לא ניתן לשינוי"

const אומר "הדבר הזה קבוע, אסור לשנות אותו". המהדר יעצור בשגיאה כל ניסיון לשנות.

const int MAX = 100;   // MAX קבוע
void print(const Point& p);   // מבטיח: הפונקציה לא תשנה את p

שימוש חשוב: כשמעבירים אובייקט לפונקציה כ-const Type&, זה אומר "אני מקבל את המקור (בלי עותק) אבל מבטיח לא לגעת בו". תראי את זה בכל מקום בהמשך.

6. העברת פרמטרים — by value מול by reference

כשמעבירים ארגומנט לפונקציה, יש שתי דרכים:

by value (Point p)by reference (Point& p)
מה עוברעותק של האובייקטהאובייקט המקורי עצמו
שינוי בפונקציהלא משפיע על המקורמשפיע על המקור
יוצר עותק?כן (מפעיל בנאי העתקה)לא

זו אחת הנקודות הכי נבחנות. by value = "צילום" שאפשר לשנות בלי לפגוע במקור, אבל עולה זמן ליצור. by reference = עבודה על המקור עצמו. הוספת const ל-reference נותנת את הטוב משני העולמות: בלי עותק, אבל בטוח מפני שינוי.

7. פונקציה, מתודה, ופונקציה חופשית

פונקציה = קטע קוד עם שם שאפשר להפעיל. ב-C++ יש שני סוגים שחשוב להבחין ביניהם:

מתודה (member function)פונקציה חופשית (global / free)
שייכת למחלקה?כןלא — עומדת בפני עצמה
איך קוראים להדרך אובייקט: p.Print()לבד: Print(p)
גישה לשדות privateיש (היא חלק מהמחלקה)אין (אלא אם היא friend)

כל ההבדל: מתודה נקראת עם נקודה על אובייקט; פונקציה חופשית נקראת לבד. זה יהיה מכריע בהעמסת אופרטורים (מודול 3).

8. this — המצביע לאובייקט הנוכחי

כשמפעילים מתודה על אובייקט, איך המתודה יודעת על איזה אובייקט היא עובדת? אותה מתודה בדיוק משמשת את כל האובייקטים:

Point a, b;
a.set(0,0);   // אותו קוד...
b.set(9,9);   // ...אבל צריך לשנות אובייקט אחר

הפתרון: בכל מתודה קיים מצביע מוסתר בשם this, שמצביע על האובייקט שעליו קראו. ב-a.set(...) המילה this מתייחסת ל-a; ב-b.set(...) ל-b. מכיוון ש-this הוא מצביע, כדי לקבל את האובייקט עצמו כותבים *this. לכן נפוץ לראות return *this; — "החזר את האובייקט הנוכחי".

void setValue(int value){
    this->value = value;  // this->value = השדה, value = הפרמטר (אותו שם)
}

9. friend — רשות גישה מיוחדת

שדות private מוסתרים: רק מתודות המחלקה יכולות לגעת בהם. אבל לפעמים פונקציה חופשית (שהיא "מבחוץ") צריכה בכל זאת לגשת אליהם — למשל פונקציה שמדפיסה את האובייקט וחייבת לקרוא את השדות הפרטיים. הפתרון: המחלקה מכריזה עליה כ-friend — "לפונקציה הזו אני נותנת רשות מיוחדת". כמו לתת לחבר מפתח לבית: הוא לא בן-בית (לא מתודה), אבל נתת לו גישה במפורש.

class Point {
    int x, y;                                 // private — מוסתר
    friend void Print(const Point& p);   // "ל-Print מותר לגשת ל-x,y שלי"
};

10. אופרטור אונרי מול בינארי

אופרטור הוא סימן שמבצע פעולה (+, -, ==). מספר האופרנדים (הדברים שהוא פועל עליהם) קובע את הסוג:

אונרי (unary)בינארי (binary)
אופרנד אחדשני אופרנדים
-a , !x , a++a + b , a == b , a = b

בדיוק כמו במתמטיקה: חיבור צריך שני מספרים (בינארי), מינוס-סימן צריך רק אחד (אונרי). ההבחנה חשובה כי אופרטורים אונריים ובינאריים נכתבים אחרת (מודול 3).

11. bool והדפסתו כ-0/1

bool הוא טיפוס שיכול להכיל רק שני ערכים: true (אמת) או false (שקר). אופרטורי השוואה כמו == ו-!= מחזירים bool.

נקודה שמבלבלת: כשמדפיסים bool עם cout, הוא מומר אוטומטית ל-int — false הופך ל-0 ו-true הופך ל-1. לכן הדפסה של תוצאת השוואה מציגה ספרה, לא את המילה "true"/"false":

cout << (5 == 5);   // true → מודפס 1
cout << (5 == 3);   // false → מודפס 0

זה חשוב בשאלות "מה יודפס" שמכניסות השוואה ישירות ל-cout (למשל שאלה 15) — התוצאה תהיה רצף של 0 ו-1.

סיכום המושגים מצביע = משתנה שמחזיק כתובת. reference = שם נוסף למשתנה. new/delete = הקצאה/שחרור זיכרון ידני. const = לא ניתן לשינוי. מתודה = פונקציה של מחלקה (נקראת עם נקודה); פונקציה חופשית = עומדת לבד. this = מצביע לאובייקט הנוכחי. friend = רשות גישה ל-private. אונרי = אופרנד אחד; בינארי = שניים.

מודול 1 · יסודות OOP ומחלקות

מה זו מחלקה, מה זה אובייקט, ולמה מסתירים נתונים.

למה בכלל OOP?

בתכנות "רגיל" (פרוצדורלי) יש נתונים בצד אחד ופונקציות שפועלות עליהם בצד אחר, והכול פתוח לכולם. ככל שהתוכנית גדלה, קשה לעקוב מי משנה מה, וקל לקלקל נתונים. תכנות מונחה עצמים (OOP) פותר את זה: אורזים יחד את הנתונים ואת הפעולות עליהם ל"יחידה" אחת (מחלקה), ומגבילים מי יכול לגעת בנתונים. זה עושה קוד מסודר, בטוח יותר, וקל יותר לתחזוקה.

מחלקה ואובייקט

מחלקה (class) היא תבנית: היא מגדירה אילו נתונים (שדות / data members) ואילו פעולות (מתודות) יהיו לאובייקט. אובייקט הוא מופע ממשי שנוצר מהתבנית. כמו שהמילה "מכונית" היא מושג כללי, אבל המכונית שחונה למטה היא אובייקט קונקרטי. ממחלקה אחת אפשר ליצור אינספור אובייקטים, ולכל אחד ערכים משלו.

class Car {
    int speed;        // שדה (data member)
public:
    void accelerate() { speed++; }  // מתודה
};

int main() {
    Car c;           // c הוא אובייקט מסוג Car
    c.accelerate();
}

הסתרת מידע (Encapsulation) — public מול private

לכל שדה/מתודה יש רמת גישה. private = נגיש רק מתוך המחלקה עצמה. public = נגיש לכולם. ברירת המחדל ב-class היא private (ב-struct היא public — נקודה שנבחנת!).

הרעיון של הסתרת מידע: שומרים את השדות private, וחושפים כלפי חוץ רק מתודות שמבצעות בקרה. כך אי אפשר להכניס נתון לא תקין.

class Student {
    int age;                 // מוסתר
public:
    void setAge(int a) {
        if (a >= 0) age = a;  // בקרת תקינות
    }
};
מלכודת מבחן אם משאירים שדה public, כל קוד יכול לשנות אותו לערך לא תקין. "התיקון הנכון להסתרה" הוא תמיד להפוך את השדה ל-private ולהוסיף מתודה שבודקת תקינות — לא הערה בקוד, ולא רק החלפת טיפוס.

this — המצביע לאובייקט הנוכחי

בתוך מתודה, this הוא מצביע לאובייקט שעליו הופעלה המתודה (הוסבר במלואו במודול 0). שני שימושים נפוצים: להחזיר את האובייקט עצמו (return *this;) כדי לאפשר שרשור קריאות; וכשלפרמטר ולשדה יש אותו שם — this->value מבדיל בין השדה (this->value) לפרמטר (value).

Cost& increase(){ value++; return *this; }
// מאפשר שרשור: c.increase().increase().increase();

העברת פרמטרים: by value מול by reference

זו נקודה קריטית בכל המבחן (הרחבה מלאה במודול 0):

by value (Car c)by reference (Car& c)
מה עוברעותק של האובייקטהאובייקט המקורי עצמו
שינוי בפונקציהלא משפיע על המקורמשפיע על המקור
מפעיל בנאי העתקה?כן (יוצר עותק)לא
זכריהעברה by value יוצרת עותק (מפעילה copy constructor) ועלולה לגרום ל-slicing בירושה. נחזור לזה במודול 6.

ארבע הדרכים להעביר פרמטר (המטריצה המלאה)

מעבר ל-by value מול by reference, המצגות מציגות ארבע חתימות אפשריות. ההבחנה: האם עובר עותק, והאם אפשר לשנות את המקור ואת המצביע.

חתימהמה עוברשינוי האובייקט המקורי?
f(Point x)עותק של האובייקטלא — עובדים על עותק
f(Point& x)האובייקט המקורי (כינוי)כן
f(Point* x)עותק של המצביע (הכתובת)כן! דרך x->Set(...)
f(Point*& x)המצביע המקורי עצמוכן, וגם אפשר להפנות אותו לאובייקט אחר (reseat)
מלכודת מבחן — מצביע by value f(Point* x) מעביר עותק של הכתובת, אבל העותק עדיין מצביע על אותו אובייקט — אז x->Set(9,9) כן משנה את המקור! הטעות הנפוצה: "העברתי מצביע by value אז שום דבר לא ישתנה". זה נכון רק אם משנים את המצביע עצמו (x = ...), לא את מה שהוא מצביע עליו.

כלל אצבעהעבירי אובייקטים כבדים ב-const Type&: בלי עלות של עותק, ובלי סכנת שינוי מקרי.

הרכבה (Composition) — שדה שהוא אובייקט

שדה של מחלקה יכול להיות אובייקט של מחלקה אחרת. למשל Rectangle שמכיל שני Point:

class Rectangle {
    Point topLeft, bottomRight;   // שני אובייקטים כשדות
public:
    void Print() { topLeft.Print(); }  // קוראים למתודות של השדה
};

זהו יחס "יש-לו" (has-a): למלבן יש נקודות. כשמלבן נבנה, הבנאים של השדות (שתי הנקודות) רצים לפני גוף הבנאי של המלבן. נחזור להבחנה בין "יש-לו" ל"הוא-סוג-של" (ירושה) במודול 5.

ארבעת עמודי ה-OOP

מודול 2 · בנאים והרסנים

מה קורה ברגע שאובייקט נוצר, וברגע שהוא מת — ובאיזה סדר.

בנאי (Constructor)

בלי בנאי, השדות של אובייקט חדש מכילים "זבל" — ערכים אקראיים שהיו בזיכרון. הבנאי הוא מתודה מיוחדת בשם המחלקה, בלי טיפוס החזרה, שרצה אוטומטית ברגע שנוצר אובייקט. תפקידו לאתחל את השדות לערכים תקינים. אי אפשר "לשכוח" לקרוא לו — הוא רץ מעצמו.

class Point {
    int x, y;
public:
    Point(int ax, int ay) : x(ax), y(ay) {}  // init list
};

בנאי ברירת מחדל (default constructor)

בנאי ללא פרמטרים. אם לא כתבת שום בנאי, הקומפיילר מייצר default constructor אוטומטית. אבל ברגע שכתבת בנאי אחד כלשהו (עם פרמטרים) — הקומפיילר כבר לא מייצר default.

מלכודת מבחן (שאלה 1) אם למחלקה יש רק Point(int ax), אז Point p; לא מתקמפל — כי אין בנאי ברירת מחדל. זו שגיאת קומפילציה, לא ערך אקראי ולא אתחול ל-0.

רשימת אתחול (init list) — : x(ax)

הדרך המומלצת לאתחל שדות. חובה עבור שדות const, references, ואובייקטים שאין להם בנאי ברירת מחדל.

בנאי העתקה (Copy Constructor)

בנאי מיוחד שרץ כשיוצרים אובייקט חדש מתוך אובייקט קיים. הוא רץ בשלושה מצבים: Point q = p; (יצירה מאובייקט אחר), העברת אובייקט לפונקציה by value (יוצרים עותק), והחזרת אובייקט מפונקציה by value. חתימתו: Point(const Point& other).

למה בנאי ההעתקה מקבל את הפרמטר by reference? אילו הוא היה מקבל by value (Point(Point other)), אז כדי להעביר את הפרמטר היה צריך ליצור עותק — כלומר לקרוא לבנאי ההעתקה — שגם הוא היה יוצר עותק... רקורסיה אינסופית. לכן הוא חייב לקבל const Point&.

מתי חובה לכתוב בנאי העתקה בעצמך? אם המחלקה מחזיקה מצביע לזיכרון דינמי (new). בנאי ההעתקה של הקומפיילר מעתיק את המצביע עצמו (העתקה שטחית) ← שני אובייקטים מצביעים לאותו זיכרון ← אסון. אז כותבים בנאי העתקה שמקצה זיכרון חדש ומעתיק את התוכן (העתקה עמוקה). זה חלק מ-Rule of Three — מודול 9.

explicit

בנאי עם פרמטר יחיד יכול לשמש להמרה אוטומטית (implicit): הקומפיילר יהפוך 5 ל-Point לבד. המילה explicit חוסמת את ההמרה האוטומטית הזו.

מלכודת מבחן (שאלה 3) אם הבנאי מסומן explicit Point(int), אז קריאה כמו print(6) לפונקציה שמצפה ל-Point לא תתקמפל — כי ההמרה מ-int ל-Point אסורה כשהיא לא מפורשת.

הרסן (Destructor)

אם הבנאי "מכין" את האובייקט, ההרסן "מנקה" אחריו. זו מתודה בשם ~ClassName() (טילדה + שם המחלקה, בלי פרמטרים ובלי ערך החזרה) שרצה אוטומטית ברגע שאובייקט מת. תפקידה לשחרר משאבים.

ההרסן רץ בשלושה מצבים: אובייקט מקומי בסוף הבלוק שלו, delete על מצביע לאובייקט, ואובייקט גלובלי בסוף התוכנית. השימוש הכי חשוב: אם המחלקה הקצתה זיכרון ב-new (מודול 0), ההרסן חייב לשחרר אותו ב-delete[], אחרת יש דליפת זיכרון.

class Polygon {
    int size;
    Point* array;              // מצביע לזיכרון דינמי
public:
    Polygon(int n) : size(n) { array = new Point[size]; }
    ~Polygon() { if (array != NULL) delete[] array; }  // שחרור
};
מלכודת מבחן — delete[] מול delete אם הקצית מערך ב-new Point[size], חייבים לשחרר ב-delete[] (עם סוגריים). delete רגיל על מערך = התנהגות לא מוגדרת (רק האיבר הראשון מנוקה). הכלל: new→delete, new[]→delete[]. תמיד תואמים.

⭐ אתחול מול השמה — אותו =, שתי משמעויות

הסימן = יכול להפעיל שתי פעולות שונות לגמרי, תלוי אם האובייקט השמאלי נוצר עכשיו או כבר קיים:

Polygon p1(5);
Polygon p2 = p1;   // p2 נוצר עכשיו → בנאי העתקה (Copy Constructor)

Polygon p3(3);
p3 = p1;           // p3 כבר קיים → אופרטור השמה (operator=)
איך מבדילים אם ה-= מופיע בשורת ההגדרה של המשתנה (יוצרים אותו) — זה בנאי העתקה. אם המשתנה כבר הוגדר קודם וה-= בא בשורה נפרדת — זה אופרטור השמה. שתי פעולות שונות, למרות אותו סימן.

מערך אובייקטים דורש בנאי ברירת מחדל

כשיוצרים מערך של אובייקטים (סטטי או דינמי), C++ מפעילה על כל איבר את בנאי ברירת המחדל (בלי פרמטרים). לכן אם למחלקה יש רק בנאי עם פרמטרים — יצירת מערך ממנה לא מתקמפלת.

Point arr[5];          // מפעיל Point() על כל אחד מ-5 → צריך בנאי ברירת מחדל
Point* p = new Point[5]; // אותו דבר, דינמי
אל תתבלבליnew Point[5] = מערך של 5 נקודות (בנאי ברירת מחדל לכל אחת). new Point(5) = נקודה אחת שנבנית עם הפרמטר 5. סוגריים מרובעים מול עגולים משנים הכול.

ארגומנטים דיפולטיביים בבנאי

אפשר לתת לפרמטר ערך ברירת מחדל, כך שאפשר להשמיט אותו בקריאה. זה מנגנון נפרד מעומס בנאים:

Point(int x, int y, bool print = true);  // print אופציונלי
Point a(1, 2);        // print מקבל true אוטומטית
Point b(1, 2, false); // מציינים במפורש

⭐ סדר בנאים והרסנים בירושה

זו אחת השאלות הכי נפוצות. הכלל:

הכלל הזהב בנייה: מלמעלה למטה — קודם מחלקת הבסיס, אחר כך היורשת.
הריסה: בסדר הפוך — קודם היורשת, אחר כך הבסיס.

struct A { A(){cout<<"A";} ~A(){cout<<"a";} };
struct B : public A { B(){cout<<"B";} ~B(){cout<<"b";} };

int main() { B b; }   // ידפיס: ABba

בנייה: A ואז B ← "AB". הריסה (הפוך): ~B ואז ~A ← "ba". סה"כ ABba.

מודול 3 · העמסת אופרטורים

איך לגרום ל-+, [], <<, ++, = לעבוד על האובייקטים שלנו — כאילו היו טיפוסים מובנים.

מה צריך לדעת ממודול 0 לפני שממשיכים מצביע, reference, const, new/delete, מתודה מול פונקציה חופשית, this, friend, אונרי/בינארי. אם משהו מהם לא ברור — חזרי רגע למודול 0.

הרעיון והמוטיבציה

על מספרים אנחנו כותבים i + j בצורה טבעית. היינו רוצים לכתוב אותו דבר על האובייקטים שלנו:

Point p1(2,3), p2(1,6);
Point p3 = p1 + p2;   // במקום p1.add(p2)

"להעמיס אופרטור" = להגדיר פונקציה בשם operator ואחריו הסימן. כשהמהדר רואה p1 + p2, הוא מתרגם את זה לקריאה לפונקציה p1.operator+(p2). זהו כל הקסם: אופרטור הוא פשוט פונקציה עם שם מיוחד.

Point Point::operator+(const Point& p) const {
    return Point(x + p.x, y + p.y);
}

אילו אופרטורים אפשר להעמיס

כמעט את כולם: אריתמטיים (+ - * / %, ++ --, += -=...), השוואה (== != < > <= >=), לוגיים (&& ||), הזזת ביטים (<< >>), וגם = () [] -> !, המרת טיפוס, new ו-delete. מה אי אפשר: להמציא סימנים חדשים, לשנות את מספר האופרנדים, או לשנות קדימות.

⭐ ההחלטה הכי חשובה: מתודה או פונקציה חופשית?

זו הנקודה שהכי מבלבלת ותמיד נבחנת. לאופרטור בינארי יש שני אופרנדים — שמאלי וימני. הכלל: מתודה שייכת תמיד לאופרנד השמאלי (הוא ה-this). לכן:

Point z = b - a;
// b.operator-(a);    ← מתודה: b הוא this, a הפרמטר. עדיף.
// operator-(b, a);   ← פונקציה חופשית (friend), שני פרמטרים.

מתי חייבים פונקציה חופשית? כשהאופרנד השמאלי אינו האובייקט שלנו:

Point z = 5 - a;   // האופרנד השמאלי הוא int
// 5.operator-(a)   ← בלתי אפשרי! ל-int אין מתודות שנוסיף לו
// operator-(5, a)  ← חייב פונקציה חופשית, friend של Point
הכלל בקצרה אם האופרנד השמאלי הוא האובייקט שלך → עדיף מתודה. אם האופרנד השמאלי הוא טיפוס אחר (int, cout, cin) → חובה פונקציה חופשית. לכן operator<< תמיד חופשית — משמאל יש cout, לא האובייקט שלנו.

"לממש a-5 גם כמתודה וגם כפונקציה חופשית" — מה זה אומר? לא מדובר באותה פעולה פעמיים! מדובר בשני ביטויים שונים: a - 5 ו-5 - a. את a - 5 אפשר לממש כמתודה (a משמאל), אבל 5 - a חייב פונקציה חופשית (5 משמאל). כדי ששני המקרים ייראו אחיד בקוד, נהוג לממש גם את a - 5 כפונקציה חופשית — ואז יש שתי פונקציות חופשיות: אחת (Point, int) ואחת (int, Point).

חוזרים כמעט בכל שאלה:

operator[] — גישה לאיבר, והחזרת reference

כדי שנוכל לכתוב a[0] = 7 (השמה לתוך האיבר!), האופרטור חייב להחזיר reference (float&) — כלומר את המקום האמיתי בזיכרון, לא עותק. עותק (float) הוא ערך זמני שאי אפשר להשים אליו.

float& FVector::operator[](int i) {
    if (i < 0 || i >= Size) throw "Out of range";
    return Items[i];   // reference לאיבר עצמו → מאפשר a[0]=7
}
מלכודת מבחן (שאלה 5) int operator[](int i) מחזיר עותק ← אי אפשר להשים אליו. const int& מאפשר קריאה בלבד. רק int& מאפשר גם קריאה וגם כתיבה.

operator<< ו-operator>> — הדפסה וקלט

כדי לכתוב cout << p;, האופרטור חייב להיות פונקציה חופשית, כי האופרנד השמאלי הוא cout (מסוג ostream) — לא האובייקט שלנו (ראי הכלל למעלה). מגדירים אותו כ-friend כדי שיוכל לגשת לשדות ה-private, ומחזירים את הזרם כדי לאפשר שרשור.

friend ostream& operator<<(ostream& out, const FVector& a){
    for (int i=0; i<a.Size; i++) out << a.Items[i] << " ";
    return out;   // מחזיר את הזרם → מאפשר cout<<a<<b
}
friend istream& operator>>(istream& in, FVector& a){   // שים לב: a לא const — משתנה!
    for (int i=0; i<a.Size; i++) in >> a[i];
    return in;
}
מלכודת מבחן (שאלה 10) אם מממשים operator<< כמתודה, האופרנד השמאלי חייב להיות האובייקט — כלומר p << cout, לא cout << p. לכן התיקון הנכון הוא פונקציה חופשית (לרוב friend) עם חתימה ostream& operator<<(ostream&, const Point&).

בונוס למודול 10 (קבצים) מכיוון ש-ofstream (כתיבה לקובץ) יורש מ-ostream, אותו operator<< בדיוק עובד גם לכתיבה לקובץ: OutFile << vec;. כתבת אותו פעם אחת — עובד לכל זרם.

operator+ — חיבור (מקומי → by value)

יוצר אובייקט חדש עם התוצאה. מכיוון שהאובייקט נוצר מקומית, מחזירים by value:

FVector FVector::operator+(const FVector& a) const {
    FVector Temp(Size + a.Size);   // נוצר מקומית
    // ... ממלא את Temp בערכים ...
    return Temp;                     // by value
}
מלכודת מבחן — כמה בנאים/הרסנים רצים בהחזרה by value? כשמחזירים אובייקט מקומי by value ומשימים אותו למשתנה חדש (Point p3 = p1 + p2;), נוצרת שרשרת שלמה: (1) הבנאי הרגיל בונה את Temp המקומי; (2) בנאי העתקה מעתיק את Temp לאובייקט זמני שמוחזר; (3) הזמני מועתק ל-p3; (4) ההרסנים של המקומי והזמני רצים. שאלות מבחן מבקשות לספור כמה פעמים רץ כל אחד — עקבי אחרי כל אובייקט זמני שנוצר ונהרס.

operator+= ו-operator*= — משנים את *this (by reference)

אלה משנים את האובייקט הקיים ומחזירים אותו עצמו — לכן by reference:

const FVector& FVector::operator+=(float val){
    for (int i=0; i<Size; i++) Items[i] += val;
    return *this;   // אובייקט קיים → by reference
}

⭐ operator++ — קדם מול פוסט (pre/post)

איך C++ מבדילה בין ++c (קדם) ל-c++ (פוסט)? זה החלק הכי מתוחכם: הגרסה עם פרמטר int דמה היא הפוסט. הפרמטר לא באמת בשימוש — הוא רק "דגל" למהדר שזו הגרסה של c++.

קדם ++cפוסט c++

const FVector& FVector::operator++(){       // ++c
    (*this) += 1.0;

    return Temp;                 // מחזיר את הישן (by value)
}
מלכודת מבחן (שאלה 13) c++ מחזיר את הערך הישן, אבל האובייקט עצמו כן גדל. אם c=1: (c++) מחזיר 1 (ו-c נעשה 2), ואז (++c) מגדיל ל-3 ומחזיר 3. תוצאה: 1 3.

operator== ו-operator!= — משתמשים זה בזה

מגדירים את == פעם אחת, ואת != פשוט דרכו — כדי לא לשכפל לוגיקה:

int FVector::operator==(const FVector& a) const {
    if (Size != a.Size) return false;
    for (int i=0; i<Size; i++)
        if (Items[i] != a.Items[i]) return false;
    return true;
}
int FVector::operator!=(const FVector& a) const {
    return !(*this == a);   // משתמש ב-== שכבר כתבנו
}

⭐⭐ operator= — אופרטור ההשמה (החלק הכי מסוכן)

זו ליבת המודול. הבעיה מתעוררת כשלמחלקה יש מצביע לזיכרון דינמי (new). אופרטור ההשמה שהמהדר נותן בחינם עושה העתקה שטחית (shallow): מעתיק את המצביע, כך ששני האובייקטים מצביעים לאותו זיכרון. תוצאה: מחיקה כפולה (crash) ודליפות. חייבים לכתוב אותו בעצמנו, עם כל מקרי הקצה:

const FVector& FVector::operator=(const FVector& a){
    if (&a != this){          // 1. הגנה מהשמה עצמית a=a
        delete[] Items;       // 2. שחרור הזיכרון הישן
        Size = a.Size;
        Items = new float[Size];   // 3. הקצאה חדשה
        for (int i=0; i<Size; i++) // 4. העתקה עמוקה
            Items[i] = a.Items[i];
    }
    return *this;             // 5. by reference → מאפשר a=b=c
}

חמש הנקודות, כל אחת היא שאלת מבחן פוטנציאלית:

הקשר ל-Rule of Three (מודול 9) אם מחלקה צריכה אחד מ-{הרסן, בנאי העתקה, operator=} — היא צריכה את שלושתם, כי לכולם אותה סיבה: ניהול נכון של המשאב הדינמי.

אידיום: בנאי העתקה שמאציל ל-operator=

כדי לא לשכפל את קוד ההעתקה העמוקה גם בבנאי ההעתקה וגם ב-operator=, אפשר לגרום לבנאי ההעתקה פשוט לקרוא ל-operator=:

FVector(const FVector& a){
    Items = NULL;   // קריטי!
    *this = a;      // מפעיל את operator= שעושה את כל העבודה
}
למה Items = NULL חובה כאן? ‎operator= מתחיל ב-delete[] Items. אבל באובייקט חדש (בתוך הבנאי) Items עדיין מכיל זבל — כתובת אקראית. delete[] על זבל = קריסה. לכן קודם מאפסים ל-NULL (מותר לעשות delete[] על NULL — זה פשוט לא עושה כלום), ורק אז קוראים ל-operator=.

operator() — אופרטור הקריאה

מעמיסים את הסוגריים עצמם, כך שאפשר "לקרוא" לאובייקט כמו לפונקציה: vec(arr, 3). שימושי גם ל-functors (מודול 11).

מינוס אונרי ואופרטור המרה

מינוס אונרי (-a) פועל על אובייקט אחד — לכן בלי פרמטרים: const FVector operator-() const;. אופרטור המרה מאפשר להשתמש באובייקט במקום שמצפים לטיפוס אחר — ולו אין טיפוס החזרה מפורש בחתימה, כי הטיפוס הוא השם עצמו:

operator const float*() const { return Items; }  // FVector יכול לשמש כ-const float*
סיכום מלכודות המבחן operator[] חייב & (reference) כדי לאפשר השמה. operator<< חייב להיות פונקציה חופשית כי cout משמאל. operator= דורש: בדיקת השמה עצמית, delete[] ישן, העתקה עמוקה, החזרה by reference. c++ מחזיר את הישן. כלל-על: אובייקט מקומי → by value; אובייקט קיים (*this) → by reference.

מודול 4 · const, static, friend וטיפול בשגיאות

מאפייני שפה נוספים שחשוב להכיר.

const על מתודה

const אומר "לא ניתן לשינוי" (יסודות במודול 0). כשמוסיפים const בסוף חתימת מתודה, זו הבטחה: "המתודה הזו לא משנה את האובייקט". התועלת: רק מתודות const מותר לקרוא על אובייקט שהוא עצמו const.

class Point {
    int x;
public:
    int getX() const { return x; }   // לא משנה כלום → const
    void setX(int v) { x = v; }        // כן משנה → בלי const
};
const Point p(5);
p.getX();   // מותר
p.setX(9); // שגיאת קומפילציה! אסור לשנות אובייקט const

static — משותף לכל האובייקטים

בדרך כלל לכל אובייקט יש עותק משלו של כל שדה. שדה static הוא היוצא מן הכלל: יש ממנו עותק אחד בלבד המשותף לכל אובייקטי המחלקה. דוגמה קלאסית: לספור כמה אובייקטים נוצרו — מגדילים מונה static בכל בנאי.

class Widget {
    static int count;   // עותק אחד לכל המחלקה
public:
    Widget() { count++; }
};
int Widget::count = 0;  // חייב אתחול פעם אחת מחוץ למחלקה

friend — רשות גישה ל-private

פונקציה או מחלקה שמוכרזת friend מקבלת גישה לשדות ה-private של המחלקה, למרות שאינה חלק ממנה (הוסבר במלואו במודול 0). השימוש הכי נפוץ: operator<< — פונקציה חופשית שצריכה לקרוא את השדות כדי להדפיס (מודול 3).

המרות אוטומטיות (auto-casting) ו-explicit

בנאי עם פרמטר יחיד משמש גם כ"כלל המרה": המהדר יכול להפוך אוטומטית ערך מהטיפוס לאובייקט. למשל אם יש Point(int), אז פונקציה שמצפה ל-Point תקבל גם int ותמיר אותו לבד. המילה explicit לפני הבנאי חוסמת את ההמרה הסמויה הזו ומחייבת המרה מפורשת.

⭐ טיפול בשגיאות — חריגים (exceptions)

throw זורק חריג, try/catch תופס אותו. נקודה שנבחנת: מה קורה אם נזרק חריג בתוך בנאי?

כלל קריטי אם נזרק חריג בתוך הבנאי, האובייקט לא נבנה במלואו — ולכן ההרסן שלו לא ייקרא. (הרסן רץ רק על אובייקט שהבנייה שלו הושלמה.)

class X {
public:
    X() { cout<<"C"; throw 7; }  // זורק באמצע הבנייה
    ~X() { cout<<"D"; }
};
int main() {
    try { X x; }
    catch(int) { cout<<"E"; }
}   // ידפיס: CE  (ה-D לא מודפס!)

ה-"C" מודפס, אז נזרק חריג ← הבנייה נכשלה ← אין הרסן ← אין "D". ה-catch מדפיס "E". סה"כ CE.

מודול 5 · ירושה ורמות גישה

מחלקה יורשת מקבלת את התכונות של מחלקת הבסיס — אבל סוג הירושה משנה את הנגישות.

מה זו ירושה ולמה

לפעמים מחלקה חדשה היא "סוג של" מחלקה קיימת: כלב הוא סוג של חיה, מלבן הוא סוג של צורה. ירושה מאפשרת למחלקה חדשה (היורשת / derived) לקבל בחינם את כל השדות והמתודות של מחלקה קיימת (הבסיס / base), ולהוסיף או לשנות עליהם. היתרון: לא משכפלים קוד — כותבים את המשותף פעם אחת בבסיס, ואת הייחודי ביורשת.

ירושה בסיסית

class Animal { public: void eat(){} };
class Dog : public Animal {  // Dog יורש מ-Animal
    public: void bark(){}
};

מודול 6 · פולימורפיזם

הלב של OOP: איך virtual גורם להתנהגות להיקבע לפי הטיפוס האמיתי בזמן ריצה. המודול הכי חשוב במבחן.

מה זה פולימורפיזם

"פולימורפיזם" = "צורות רבות". הרעיון: אותה קריאה בקוד יכולה להתנהג אחרת, בהתאם לאובייקט האמיתי שמאחוריה. למשל, לולאה שעוברת על אוסף צורות וקוראת לכל אחת draw() — מלבן יצייר מלבן, מעגל יצייר מעגל, אף שהקוד זהה.

הבעיה שפולימורפיזם פותר

מצביע מסוג Base* יכול להצביע על אובייקט Derived (כי היורשת "היא סוג של" הבסיס). השאלה: כשקוראים דרכו למתודה, איזו גרסה תרוץ — של Base או של Derived?

שני "טיפוסים" לאותו משתנה טיפוס סטטי = הטיפוס שכתוב בקוד (טיפוס המצביע), נקבע בקומפילציה. טיפוס דינמי = סוג האובייקט האמיתי שאליו מצביעים בפועל, בזמן ריצה. ב-Base* p = &d; (כאשר d הוא Derived): הטיפוס הסטטי הוא Base*, הדינמי הוא Derived. כל השאלה של virtual היא: לפי איזה מהשניים נבחרת המתודה.

⭐ virtual — הכלל

הכלל הזהב של virtual מתודה לא virtual: הגרסה נבחרת לפי הטיפוס הסטטי (טיפוס המצביע/משתנה) — בזמן קומפילציה.
מתודה virtual: הגרסה נבחרת לפי הטיפוס הדינמי (האובייקט האמיתי) — בזמן ריצה.

class Base {
public:
    void f(){cout<<"Bf";}          // לא virtual
    virtual void g(){cout<<"Bg";}  // virtual
};
class Derived : public Base {
public:
    void f(){cout<<"Df";}
    void g(){cout<<"Dg";}
};
Derived d;
Base* p = &d;
p->f();   // לא virtual → לפי הטיפוס Base* → "Bf"
p->g();   // virtual → לפי האובייקט האמיתי Derived → "Dg"
// סה"כ: BfDg

כאן מוסתרת שאלה 6.

⭐ slicing — "חיתוך" בהעברה by value

אם מעבירים אובייקט Derived לפונקציה שמקבלת Base by value, נוצר עותק מסוג Base בלבד — החלק של Derived "נחתך". לכן גם מתודה virtual תריץ את גרסת ה-Base.

class Animal {
public:
    virtual void speak(){ cout<<"sound"; }
};
class Dog : public Animal {
public:
    void speak(){ cout<<"Woof"; }
};

void byValue(Animal a){ a.speak(); }   // by value
void byRef(Animal& a){ a.speak(); }   // by reference

Dog d;
byValue(d);   // "sound" ← slicing! החלק של Dog נחתך
byRef(d);     // "Woof"  ← עובד, זו הפניה לאובייקט האמיתי

למה byValue מדפיס "sound"? הפרמטר Animal a הוא עותק בגודל Animal. כשמעבירים את הכלב, רק החלק של Animal נכנס לעותק — החלק הייחודי של Dog לא נכנס ל"קופסה" בגודל Animal ונחתך. העותק הוא Animal טהור, כבר לא כלב, ולכן speak() מריץ את גרסת Animal — גם ש-speak היא virtual.

למה byRef מדפיס "Woof"? הפניה לאובייקט האמיתי, בלי עותק — הכלב נשאר כלב. virtual בוחר לפי האובייקט האמיתי, אז רצה גרסת Dog. הכלל: virtual עוזר רק דרך מצביע או reference; העתקה לתוך טיפוס הבסיס תמיד חותכת.

מלכודת מבחן (שאלה 18) פולימורפיזם עובד רק דרך מצביע או reference. void foo(Base b) מקבל עותק by value ← slicing ← מדפיס "B" גם אם f היא virtual. אם היה כתוב Base& b — היה מדפיס "D".

⭐ הרסן וירטואלי

אם מוחקים אובייקט דרך Base*, וההרסן של Base אינו virtual — רק הרסן ה-Base ירוץ, וההרסן של Derived לא. תוצאה: דליפת משאבים של Derived. הפתרון: להפוך את הרסן הבסיס ל-virtual.

נראה את זה על דוגמה מלאה. כאן ל-Derived יש שדה פרטי int* p — מצביע למערך דינמי של 10 מספרים, שהוקצה ב-new בבנאי ואמור להשתחרר ב-delete[] p בהרסן:

class Base {
public:
    ~Base(){ cout<<"B"; }        // לא virtual!
};
class Derived : public Base {
    int* p;                          // המשאב הדינמי של Derived
public:
    Derived(){ p = new int[10]; }   // הבנאי מקצה מערך
    ~Derived(){ delete[] p; cout<<"D"; }  // ההרסן משחרר אותו
};

Base* b = new Derived;   // אובייקט Derived, מצביע מסוג Base*
delete b;                // מוחקים דרך מצביע בסיס → מדפיס רק "B"!

מה משתבש: ההרסן של Base אינו virtual, אז המחיקה דרך Base* נבחרת לפי טיפוס המצביע — רץ רק ~Base(), ו-~Derived() לא רץ כלל. לכן delete[] p שבתוכו אף פעם לא מתבצע, והמערך של 10 המספרים נשאר תפוס לנצח — דליפת זיכרון. (וגם ה-"D" לא מודפס, רק "B".)

הפתרון: להפוך את הרסן הבסיס ל-virtual ~Base(). אז המחיקה הופכת פולימורפית ונבחרת לפי האובייקט האמיתי — קודם רץ ~Derived() (שמשחרר את p), ואז ~Base() מופעל אוטומטית אחריו. אין דליפה, ומודפס "DB".

זכרי — הרסן הבסיס תמיד מופעל אוטומטית ברגע שהרסן היורשת רץ, הרסן הבסיס מופעל אחריו לבד, תמיד (סדר הפוך לבנייה). הבעיה בשאלה 8 היא לא ש-~Base חסר — אלא ש-~Derived בכלל לא מתחיל לרוץ בלי virtual.

מלכודת מבחן (שאלה 8) delete b; כאשר b הוא Base* שמצביע על Derived, ולבסיס אין הרסן וירטואלי ← המשאב של Derived (המערך p) עלול לא להשתחרר. זו הבעיה המהותית.

מחלקות אבסטרקטיות ומתודות pure virtual

virtual double area() const = 0; היא מתודה pure virtual — בלי מימוש. מחלקה עם מתודה כזו היא אבסטרקטית ואי אפשר ליצור ממנה אובייקט. מחלקה יורשת חייבת לממש את כל המתודות ה-pure virtual, אחרת גם היא נשארת אבסטרקטית.

מה זה ה-= 0? ה-= 0 בסוף החתימה הוא בדיוק מה שהופך את המתודה ל-pure virtual. הוא לא מציב ערך ולא קשור למספר אפס — זה תחביר מיוחד שאומר "למתודה הזו אין מימוש כאן, וכל מחלקה יורשת חייבת לספק אותו". מתודה עם = 0 מכריחה את היורשות לממש, ולכן הבסיס עצמו הופך לאבסטרקטי (תבנית שאי אפשר ליצור ממנה אובייקט ישירות).

class Shape {                       // אבסטרקטית
public:
    virtual double area() const = 0;   // pure virtual — בלי גוף
};
class Circle : public Shape {
    double r;
public:
    Circle(double radius) : r(radius) {}
    double area() const { return 3.14 * r * r; }  // מספק מימוש → Circle כבר לא אבסטרקטית
};

Shape s;        // ❌ שגיאה — אי אפשר ליצור אובייקט ממחלקה אבסטרקטית
Circle c(5);   // ✅ מותר — Circle מימשה את area
מלכודת מבחן (שאלה 17) אם Circle יורשת מ-Shape האבסטרקטית אבל לא מממשת את area(), אז Circle עדיין אבסטרקטית ← Circle c; הוא שגיאת קומפילציה.

typeid ו-dynamic_cast (RTTI)

אלה שני כלים לבדוק, בזמן ריצה, מה הטיפוס האמיתי שמאחורי מצביע בסיס.

dynamic_cast הוא המרה בטוחה בזמן ריצה של מצביע בתוך היררכיית ירושה. השימוש הנפוץ: יש לך מצביע בסיס (Animal*) ואת רוצה להתייחס אליו כאל הטיפוס הנגזר (Dog*) — למשל כדי לקרוא למתודה שקיימת רק ב-Dog. הוא בודק בזמן ריצה אם האובייקט האמיתי הוא מהטיפוס המבוקש: אם כן — מחזיר מצביע תקין; אם לא — מחזיר NULL, כדי שלא תקרסי. הסוגריים המשולשים <> מציינים את טיפוס היעד: dynamic_cast<Dog*>(a) = "נסה להמיר את a ל-Dog*".

class Animal { public: virtual ~Animal(){} };
class Dog : public Animal { public: void bark(){ cout<<"Woof"; } };
class Cat : public Animal {};

Animal* a = new Dog;                // מצביע בסיס שמצביע על כלב

Dog* d = dynamic_cast<Dog*>(a);   // האובייקט באמת כלב → מצביע תקין
if (d != NULL) d->bark();          // "Woof"

Cat* c = dynamic_cast<Cat*>(a);   // האובייקט אינו חתול → NULL
if (c == NULL) cout<<"not a cat";

אותו תחביר בדיוק בשתי ההמרות — אבל התוצאה תלויה באובייקט האמיתי. ההמרה ל-Dog* מצליחה כי a הוא כלב; ההמרה ל-Cat* מחזירה NULL כי a אינו חתול (Dog ו-Cat הם "אחים" נפרדים). ה-NULL הוא לא באג — זו התכונה של dynamic_cast: הוא מודיע לך שההמרה לא חוקית, במקום לקרוס.

typeid(*p) מחזיר את הטיפוס המדויק של האובייקט. ההבדל המהותי מ-dynamic_cast: typeid דורש התאמה מדויקת, בעוד dynamic_cast מסתפק ב"הוא סוג של".

RTTI עובד רק על מחלקות פולימורפיות ‎dynamic_cast ו-typeid עובדים רק על מחלקות פולימורפיות — כאלה עם לפחות מתודה virtual אחת. לכן ל-Animal יש הרסן virtual: הוא הופך אותה לפולימורפית וכך מאפשר בכלל את ה-RTTI. (וזו גם הסיבה הכללית — הרסן וירטואלי מבטיח מחיקה בטוחה דרך מצביע בסיס.) בלי אף מתודה וירטואלית, המהדר לא יאפשר dynamic_cast על האובייקט.

מלכודת מבחן (שאלה 15) 
class Person   { public: virtual ~Person(){} };
class Employee  : public Person   {};
class Developer : public Employee {};

Person* p = new Developer;   // p: מצביע Person על אובייקט Developer
cout << (typeid(*p) == typeid(Employee));      // שורה א
cout << (dynamic_cast<Employee*>(p) != NULL);  // שורה ב
ההיררכיה: Developer ← Employee ← Person, והאובייקט האמיתי הוא Developer.
• שורה א — typeid דורש טיפוס מדויק: הטיפוס האמיתי הוא Developer, לא Employee ← 0.
• שורה ב — Developer הוא כן סוג של Employee ← ההמרה מצליחה ← לא NULL ← 1.
תוצאה: 01. אותו אובייקט נותן 0 ל-typeid ו-1 ל-dynamic_cast, כי אחד דורש התאמה מדויקת והשני מסתפק ב"הוא סוג של".

מודול 7 · ירושה מרובה ויהלום המוות

כשמחלקה יורשת מכמה מחלקות — סדר בנייה, דו-משמעות, ו-virtual inheritance.

ירושה מרובה

מחלקה יכולה לרשת מכמה מחלקות בבת אחת: class C : public A, public B.

⭐ סדר בנייה בירושה מרובה

הכללהבסיסים נבנים לפי סדר ההכרזה ברשימת הירושה (לא לפי סדר ה-init list), ואז המחלקה עצמה. ההריסה — הפוך.

struct C : public A, public B { ... };
// בנייה: A, B, C  →  "ABC"
// הריסה: ~C, ~B, ~A  →  "cba"
// C c;  ידפיס:  ABCcba

כאן מוסתרת שאלה 11.

⭐ יהלום המוות (Diamond Problem)

כש-D יורשת מ-B ומ-C, ושתיהן יורשות מ-A — ל-D יש שני עותקים של A. לכן פנייה לשדה של A (כמו d.x) היא דו-משמעית ← שגיאת קומפילציה.

struct A { int x; };
struct B : public A {};
struct C : public A {};
struct D : public B, public C {};
D d; d.x = 5;  // שגיאה! x דו-משמעי (שני A-ים)

כאן מוסתרת שאלה 12.

⭐ virtual inheritance — הפתרון ליהלום

אם B ו-C יורשות מ-A בירושה virtual, אז ל-D יש עותק אחד בלבד של A. הדו-משמעות נעלמת. ובנוסף — הבנאי של A מופעל פעם אחת בלבד, ישירות ע"י המחלקה הכי-נגזרת (D), לפני B ו-C.

struct B : virtual public A {...};
struct C : virtual public A {...};
struct D : public B, public C {...};
// D d;  →  A נבנה פעם אחת ראשון:  ABCD
מלכודת מבחן (שאלה 14) עם virtual inheritance, A נבנה פעם אחת ראשון (לא פעמיים). הסדר: A, ואז B, ואז C, ואז D ← ABCD. בלי virtual היה יוצא ABAC... (A פעמיים).

⭐ בנאי בירושה וירטואלית — מי קורא לבנאי של האב?

נקודה עדינה שנובעת מכך ש-A נבנה פעם אחת בלבד: בירושה רגילה, כל מחלקה קוראת לבנאי של האב שלה. אבל בירושה וירטואלית, אם A מקבל פרמטרים בבנאי, ו-B1 קורא A(1) ו-B2 קורא A(2) — למי להאמין? זו אי-ודאות.

הכלל: בירושה וירטואלית, האחריות לקרוא לבנאי של האב המשותף עוברת למחלקה הכי-נגזרת (C). הקריאות של B1 ו-B2 ל-A מתעלמים מהן, ו-C חייבת לקרוא ל-A ישירות ב-init list שלה.

class A {
    int x;
public:
    A(int ax) : x(ax) {}          // לבנאי יש פרמטר
};
class B1 : virtual public A {
public:
    B1() : A(1) {}              // מתעלמים מזה בירושה וירטואלית
};
class B2 : virtual public A {
public:
    B2() : A(2) {}              // גם מזה
};

class C : public B1, public B2 {};      // ❌ שגיאה — A חסר בנאי ברירת מחדל ו-C לא קוראת לו

class C : public B1, public B2 {
public:
    C() : A(0) {}               // ✅ הפתרון — C קוראת ל-A ישירות
};
מלכודת מבחן בירושה וירטואלית, המחלקה הכי-נגזרת חייבת לקרוא בעצמה לבנאי של האב המשותף. אם ל-A אין בנאי ברירת מחדל ו-C לא קוראת ל-A(...) ← שגיאת קומפילציה, למרות ש-B1 ו-B2 "כאילו" קוראות לו.

מתי כפילות של האב היא דווקא רצויה?

המדריך הציג את היהלום כבעיה — אבל לא תמיד. לפעמים שני עותקים של האב הם בדיוק מה שרוצים, ואז לא משתמשים ב-virtual inheritance:

מקרהעותק כפול של האבמה עושים
שעון Rolex שיורש מ-AnalogClock ו-DigitalClock (שניהם יורשים מ-Time)רצוי — כל תצוגה שומרת זמן משלהירושה רגילה (שני עותקי Time)
ElectricBaseGuitar שיורש מ-ElectricGuitar ו-BaseGuitar (שניהם יורשים מ-Guitar)באג — גיטרה אחת, לא שתייםירושה virtual (עותק אחד)

המסקנה: virtual inheritance היא לא "תמיד נכונה". משתמשים בה רק כשעותק אחד של האב המשותף הוא ההגיוני. כשכל תת-אובייקט אמור להיות עצמאי — משאירים ירושה רגילה.

מודול 8 · Templates (תבניות)

קוד כללי שעובד על כל טיפוס בלי לשכפל אותו.

הרעיון

במקום לכתוב maxInt, maxDouble וכו', כותבים פעם אחת עם טיפוס כללי T, והקומפיילר מייצר גרסה לכל טיפוס שמשתמשים בו.

template <class T>
T maxT(T a, T b) {
    return (a < b) ? b : a;
}
maxT(3, 7);      // T=int
maxT(3.5, 7.2);  // T=double

⭐ הסקת טיפוס (type deduction)

הקומפיילר מסיק את T מהארגומנטים. אם יש T אחד בחתימה אבל הארגומנטים הם מטיפוסים שונים, אין דרך להחליט מהו T ← שגיאת קומפילציה.

מלכודת מבחן (שאלה 7) maxT(1, 2.5): הארגומנט הראשון int, השני double, אבל שניהם חייבים להיות אותו T ← הקומפיילר לא יכול להסיק T יחיד ← שגיאת קומפילציה. (אין המרה אוטומטית ב-template כדי "ליישר" את הטיפוסים.)

⭐ דרישות מהטיפוס T

ה-template משתמש באופרטורים על T (למשל ==, <<). הקוד מתקמפל רק כשמייצרים ממנו גרסה עבור טיפוס שתומך באותם אופרטורים. אם הטיפוס לא תומך — השגיאה מתגלה ברגע ה-instantiation (יצירת הגרסה), בזמן קומפילציה.

מלכודת מבחן (שאלה 16) printIfEqual משתמש ב-a == b וב-cout << a. אם קוראים לו עם Student שאין לו operator== ו-operator<< ← שגיאת קומפילציה בעת יצירת המימוש עבור Student. זו לא שגיאת ריצה, ולא "T יכול להיות כל טיפוס".

מודול 9 · Rule of Three וניהול משאבים

מתי חובה לכתוב בעצמך בנאי העתקה, operator= והרסן.

⭐ כלל השלושה (Rule of Three)

הכלל אם מחלקה מנהלת משאב דינמי (זיכרון מ-new, קובץ פתוח וכו') וצריכה להגדיר אחד מהשלושה — כמעט תמיד היא צריכה להגדיר את כל השלושה:
1. הרסן (Destructor)
2. בנאי העתקה (Copy Constructor)
3. אופרטור השמה (operator=)

למה? כי אחרת הקומפיילר מייצר גרסאות שמעתיקות את המצביע עצמו (העתקה שטחית), ואז שני אובייקטים מצביעים לאותו זיכרון ← מחיקה כפולה / דליפות.

⭐ Rule of Three בירושה

העובדה שמחלקת הבסיס מקיימת Rule of Three לא פותרת את הבעיה עבור מחלקה יורשת שמוסיפה משאב דינמי משלה. היורשת צריכה את השלושה שלה עבור המשאב החדש.

מלכודת מבחן (שאלה 20) NamedBuffer יורשת מ-Buffer (שיש לו Rule of Three), ומוסיפה שדה דינמי char* name עם הרסן שמשחרר אותו. חסר לה בנאי העתקה ו-operator= משלה עבור name — אחרת העתקה של NamedBuffer תעתיק את המצביע name באופן שטחי ← מחיקה כפולה.

מודול 10 · קבצים ו-serialization

נמצא בסילבוס (לא בשאלות התרגול) — כיסוי מלא ליתר ביטחון.

זרמים (streams)

C++ עובדת עם קבצים דרך זרמים, בדיוק כמו cin/cout: ofstream לכתיבה, ifstream לקריאה, fstream לשניהם. כולם ב-<fstream>.

// כתיבה לקובץ
ofstream out("data.txt");
if (out.is_open()) {
    out << "Hello" << 42 << endl;
    out.close();
}

// קריאה מקובץ
ifstream in("data.txt");
string word; int n;
in >> word >> n;

אותם אופרטורים כמו במסך

מכיוון ש-ofstream יורש מ-ostream, אותו operator<< שכתבנו למחלקה (מודול 3) עובד גם לכתיבה לקובץ. זה היופי של הירושה בזרמים.

serialization (סריאליזציה)

המרה של אובייקט לרצף בייטים/טקסט שאפשר לשמור לקובץ, ואז לשחזר ממנו. הדרך הפשוטה: לכתוב מתודה save(ostream&) שכותבת את השדות, ומתודה load(istream&) שקוראת אותם באותו סדר.

קריאה בטקסט מול בינארי קריאה/כתיבה טקסטואלית (<<, >>) קריאה לאדם. כתיבה בינארית (write/read) מהירה וקומפקטית אבל לא קריאה. לשמירת אובייקטים שלמים לרוב משתמשים בבינארי.

מודול 11 · STL — הספרייה הסטנדרטית

נמצא בסילבוס (לא בשאלות התרגול) — כיסוי מלא ליתר ביטחון.

מה זה STL

Standard Template Library — אוסף מבני נתונים ואלגוריתמים מוכנים, בנויים על templates, כך שהם עובדים על כל טיפוס.

מכולות (containers) נפוצות

מכולהמה זה
vectorמערך דינמי (גודל משתנה)
listרשימה מקושרת דו-כיוונית
mapטבלת מפתח→ערך ממוינת
setאוסף ערכים ייחודיים ממוין
vector<int> v;
v.push_back(10);

איטרטורים (iterators)

אובייקט שמצביע לאיבר במכולה ומאפשר לעבור עליה — כמו מצביע כללי. begin() מחזיר איטרטור לאיבר הראשון, end() ל"אחרי האחרון".

for (vector<int>::iterator it = v.begin(); it != v.end(); ++it)
    cout << *it;

Functors (אובייקטי פונקציה)

אובייקט שאפשר "לקרוא לו" כמו פונקציה, כי הוא מעמיס את operator(). שימושי כדי להעביר לוגיקה לאלגוריתמים.

struct IsEven {
    bool operator()(int n) const { return n % 2 == 0; }
};
IsEven f;
cout << f(4);  // קוראים לאובייקט כמו לפונקציה → 1

Lambda expressions

דרך קצרה לכתוב פונקציה אנונימית במקום (בעיקר להעביר לאלגוריתמים של STL).

auto add = [](int a, int b) { return a + b; };
cout << add(2, 3);  // 5
// [] = capture list, () = פרמטרים, {} = גוף
קשר ל-functorsLambda הוא בעצם functor שהקומפיילר יוצר עבורך מאחורי הקלעים.
